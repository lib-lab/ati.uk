# Роадмап

Каждый этап — отдельная задача на одну сессию. Перед началом прочитайте [CLAUDE.md](../CLAUDE.md): там команды, архитектура и общее определение готовности. Значения по умолчанию и трактовки ТЗ записаны в [DECISIONS.md](DECISIONS.md), в задачах на них стоят ссылки «см. DECISIONS».

Этапы идут по порядку: более поздние опираются на механизмы более ранних (тик времени из E3, уведомления из E3, размещение из E6).

## E3. Время, лог событий, события рейтинга, уведомления, пополнение баланса

**Цель.** Дать инструменты для проверки сценариев: сдвиг текущей даты, лог событий, уведомления, тестовое пополнение баланса. Эти механизмы нужны всем следующим этапам.

**Что уже есть.** `state.now` (симулированные часы), `logEvent` в `src/domain/events.ts`, типы `EventLogEntry`, `Notification`, `LedgerTransaction`; адаптер `PaymentProvider` с заглушкой `MockPayments`. Команда `openContact` уже пишет события `payment` и `contact_opened`.

**Сделать.**
1. **Тик времени.** Команда `advanceTime(state, hours)` в `src/domain/commands/time.ts`. Она двигает `now`, пишет событие `time_shifted` и прогоняет по порядку список «процессов» — чистых функций `(state, from, to) => state`. Список процессов лежит в одном месте; в E3 он пуст, кроме ежедневного пересчёта (п. 2). Следующие этапы добавляют туда свои процессы: истечение объявлений, напоминания, дайджесты, деактивацию.
2. **События рейтинга.** Обёртка над командами, которая считает рейтинги всех компаний до и после команды и для каждой изменившейся компании пишет `rating_changed`: балл до и после, компонент (если изменился один) и причину. Причина берётся у команды (например, «+ отзыв 5 от компании X»). При сдвиге времени причина — «ежедневный пересчёт» (одно событие на компанию за сдвиг, см. DECISIONS). В событии перечисляются изменившиеся компоненты с изменением их вклада в балл.
3. **Панель времени** в верхней панели: кнопки «+1 day», «+1 week», «+6 months» и текущая дата.
4. **Лог событий:** страница `/events`. Таблица: время, тип, кто, о ком (названия компаний, а не id), причина — текст из i18n с параметрами. Фильтры по типу и по компании. Новые события сверху.
5. **Уведомления.** Значок с числом непрочитанных в верхней панели и страница `/notifications` для текущей компании, с кнопкой «отметить прочитанными». Тексты уведомлений — через i18n по `type` и `params`. В E3 своих источников уведомлений нет, страница может быть пустой (с пустым состоянием).
6. **Пополнение баланса:** страница `/balance` с текущим балансом, бесплатными контактами, историей проводок и кнопками «+10 €», «+50 €», «+100 €». Пополнение сначала вызывает `adapters.payments.topUp` (асинхронно), затем доменную команду `topUp(state, companyId, amount, externalId)`: проводка `topup` и событие `balance_topup`. В состоянии «нет денег» на карточке объявления (E2) добавить ссылку «Top up balance» на `/balance`.

**Критерии готовности.**
- [x] «+1 day» меняет дату в панели и пишет `time_shifted` в лог. «+6 months» работает так же.
- [x] Сдвиг на 6 месяцев даёт события `rating_changed` с причиной «daily recalculation» хотя бы у одной компании (активность и стаж растут).
- [x] Открытие контакта и пополнение видны в логе с суммой и названиями компаний.
- [x] Войти как Moravia Trans → карточка груза → «Top up balance» → +10 € → вернуться → контакт открывается за 5 €, баланс 5 €.
- [x] Значок уведомлений и пустое состояние страницы уведомлений.
- [x] Тесты: `advanceTime` (дата, событие, вызов процессов в порядке, пересчёт только при пересечении суток), обёртка событий рейтинга (событие только при изменении, правильные до/после), `topUp` (проводка, событие, сумма > 0).

## E4. Полный поиск

**Цель.** Все фильтры и сортировки из раздела ТЗ «Поиск и подписки».

**Что уже есть.** `src/domain/rules/search.ts`: видимость, фильтры по городам, кузову и весу, сортировка «приоритет, затем дата». Страница `src/ui/pages/SearchPage.tsx`. Тип `SearchFilters` уже содержит все поля.

**Сделать.**
1. **Радиус:** «откуда» и «куда» с радиусом в км от выбранного города (`cityDistanceKm`). При радиусе 0 или пустом — точное совпадение города. Машина с «куда — любое» подходит под любой фильтр «куда».
2. **Дата или диапазон дат.** Объявление подходит, если его дата (или диапазон загрузки) пересекается с диапазоном фильтра.
3. **Объём «от — до»** (объявления без объёма при заданном фильтре объёма не показываются; записать в DECISIONS). **Способ загрузки** — достаточно пересечения.
4. **Минимальный рейтинг контрагента** и **«только без красных флагов»**. Рейтинг берётся из `computeRating`, правило фильтра получает функцию рейтинга параметром, чтобы остаться чистым.
5. **Сортировки:** по дате загрузки (по умолчанию), по ставке за км, по рейтингу, по свежести (`createdAt`). Приоритетные объявления во всех сортировках идут первыми. Объявления без ставки при сортировке по ставке идут в конце.
6. **Пустые состояния:** «объявлений нет» и «ничего не найдено по фильтрам» (сделаны в E2, проверить с новыми фильтрами).
7. **Выдача:** в строке видны маршрут, дата, кузов, вес, ставка, рейтинг и значок проверки; контакт скрыт (так уже сделано).

**Критерии готовности.**
- [ ] Каждый фильтр и каждая сортировка покрыты тестами, включая краевые случаи: «любое направление», диапазон загрузки, объявления без ставки и без объёма.
- [ ] «Только без красных флагов» убирает из выдачи Ghost Lines и Euro Cargo Partners.
- [ ] Минимальный рейтинг 80 убирает компании с баллом ниже 80.
- [ ] Радиус: тест на фикстурах — фильтр «откуда Warsaw, 150 км» включает объявление из Łódź (≈ 120 км по прямой) и не включает Kraków (≈ 250 км).
- [ ] Сортировка «по ставке за км» ставит самую дорогую ставку за км первой (после приоритетных).

## E5. Профиль компании

**Цель.** Экран 6 из ТЗ: балл, раскрытие по компонентам и событиям, отзывы, претензии, данные проверки.

**Что уже есть.** `computeRating` с компонентами, `primaryMark`. События `rating_changed` с компонентом пишутся с E3. В карточке объявления есть краткая разбивка балла.

**Сделать.**
1. Страница `/company/:id`. Ссылки на неё: название компании в карточке объявления и в выдаче, страница «Log in as».
2. Шапка: название, роль, страна, регистрационный номер, на площадке с какой даты; балл, главная отметка, число отзывов, «New member», все активные флаги.
3. **Компоненты:** для каждого — значение (или «нет данных»), номинальный и фактический вес, вклад в балл. Под компонентом раскрываются его события `rating_changed` («+ отзыв 5 от компании X», «− открытая претензия от Y»).
4. **Отзывы:** список с оценкой, автором (ссылка), датой, пометками «не учитывается: автор на проверке» и «старше 12 месяцев, вес 0,5», ответ владельца.
5. **Претензии:** список со статусами open, settled, rejected.
6. **Проверка:** запись реестра (статус, дата основания, отчётность, юридическое название, адрес), совпадение с профилем, дата проверки.
7. Блок «Подробности» в карточке объявления ведёт в профиль.

**Критерии готовности.**
- [ ] Профиль Nordic Reefer: «New member», отзывы и активность «нет данных», веса проверки и претензий 60 % и 40 %.
- [ ] Профиль Danube Haulage: компонент «Претензии» = 50, видны 2 открытые претензии.
- [ ] Профиль QuickRate Trans: жёлтый флаг, взаимный отзыв помечен как неучитываемый.
- [ ] Сумма вкладов компонентов равна баллу (с точностью до округления) — тест на функцию расчёта вкладов.

## E6. Размещение, «мои объявления», сроки жизни, продвижение

**Цель.** Экраны 2, 3 и 7 из ТЗ и правила срока жизни.

**Что уже есть.** `computeExpiresAt`, `isExpired`, `needsExpiryReminder` в `src/domain/rules/lifetime.ts` (с тестами); цены в `config.ts`; тип `RouteTemplate`; тик времени и уведомления из E3.

**Сделать.**
1. **Формы груза и машины** по таблице полей ТЗ. Обязательные поля проверяются. Город выбирается из справочника, адрес — свободный текст. Ставка: сумма, валюта (EUR), с НДС или без, способ оплаты, либо «запрос ставки» / «договорная». Размещать можно только по роли (см. DECISIONS «Кто что ищет»). Команда `postListing` пишет событие `listing_created` и считает `expiresAt`.
2. **Шаблоны маршрутов:** «сохранить как шаблон» в форме и «создать из шаблона» (список шаблонов текущей компании).
3. **«Мои объявления»** (`/my-listings`): вкладки «активные» и «снятые и истёкшие». Действия:
   - продлить (правило — см. DECISIONS «Продление»);

4. **Процессы тика:** напоминание за 24 часа до истечения (уведомление `expiry_reminder`, один раз на срок жизни) и автоматическое истечение (статус `expired`, событие `listing_expired`, уведомление `listing_expired`).

**Критерии готовности.**

- [ ] «+1 day» до последних суток → уведомление о скором истечении. Ещё «+1 day» → объявление истекло и пропало из поиска, в «моих объявлениях» есть кнопка «Extend». После продления оно снова в поиске; приоритет не перенёсся, «открытое» сохранилось.
- [ ] Снятие с причиной «found_on_platform» влияет на компонент «Активность» (событие рейтинга в логе).
- [ ] Перевозчик не может разместить груз, грузовладелец — машину.
- [ ] Тесты: валидация обязательных полей, права по роли, продление (в том числе истёкшего), снятие, оплата открытого и приоритета, процессы напоминания и истечения.

## E7. Отзывы и претензии

**Цель.** Правила отзывов и претензий из ТЗ и их влияние на рейтинг.

**Что уже есть.** Типы `Review` и `Claim`; компоненты рейтинга «Отзывы» и «Претензии»; события рейтинга (E3); профиль (E5).

**Сделать.**
1. **Оставить отзыв** (1–5 звёзд и текст) можно только при наличии `ContactAccess` автора к компании и не чаще одного раза в 90 дней на направленную пару. Форма доступна в профиле компании и в карточке объявления после открытия контакта. Если оставить нельзя, объясняется почему и когда станет можно.
2. **Ответ на отзыв:** владелец отвечает один раз, в своём профиле.
3. **Подать претензию** можно при наличии `ContactAccess`. Заявитель может отметить её урегулированной. Отклонение — у модератора (E8).
4. Каждое действие пишет событие; изменение балла — событие `rating_changed` с причиной («+ отзыв 5 от компании X», «− открытая претензия от Y», «претензия от Y урегулирована»).

**Критерии готовности.**
- [ ] Без открытого контакта форма отзыва недоступна, рядом объяснение.
- [ ] После отзыва повторный отзыв той же компании недоступен 90 дней; после «+6 months» снова доступен.
- [ ] Открытая претензия снижает балл, и это видно в логе и в профиле; после урегулирования балл возвращается.
- [ ] Тесты: допуск к отзыву (доступ, 90 дней, направление пары, отзыв о себе запрещён), ответ один раз, жизненный цикл претензии и права на переходы.

## E8. Жалобы, возвраты, модерация, флаги

**Цель.** Жалобы на объявления, возвраты, правило «3 за 30 дней», страница модератора, управление флагами, детектор связанных аккаунтов.

**Что уже есть.** Типы `Complaint` и `Flag`, `FLAG_LEVEL`, `activeFlags`, `isBlocked`; поле `ContactAccess.refundedAt` (уже учитывается в квоте); `ownerListingsHidden` учитывает `listingsHiddenUntilContactConfirmed`.

**Сделать.**
1. **Жалоба из карточки:** «неактуально» (может подать любая компания) или «контакт не отвечает или неверен» (только при открытом контакте). Одна жалоба на объявление от компании.
2. **Страница модератора** `/moderation` (доступна при входе как Moderator), три вкладки:
   - жалобы на рассмотрении: подтвердить или отклонить;
   - претензии: отклонить или отметить урегулированной;
   - флаги: поставить или снять «Заблокирован» и «На проверке»; перевести жёлтый флаг в подтверждённую накрутку.
3. **Подтверждение жалобы «не отвечает»:** возврат — проводка `refund` на сумму оплаты или возврат бесплатной квоты (правило — см. DECISIONS), `refundedAt` у доступа, уведомление `refund` заявителю, события `complaint_resolved` и `refund`.
4. **Правило «3 подтверждённые жалобы за 30 дней»:** у компании ставится `listingsHiddenUntilContactConfirmed`, ей приходит уведомление `listings_hidden`. Владелец видит баннер и кнопку «Contact data is up to date», которая снимает скрытие.
5. **Подтверждённая накрутка:** жёлтый флаг становится красным `fraud_blocked`, отзывы связанных аккаунтов помечаются `voided`, события рейтинга пишутся.
6. **Детектор связанных аккаунтов:** общий `deviceId`, взаимные отзывы, отзывы от компании без объявлений. Результат — жёлтые флаги с `source: 'detector'` и описанием признаков. Запускается ежедневным процессом тика и кнопкой на странице модератора.

**Критерии готовности.**
- [ ] Перевозчик открыл контакт за 5 € → жалоба «не отвечает» → модератор подтверждает → баланс перевозчика +5 €, уведомление, жалоба в логе.
- [ ] То же для бесплатного открытия: счётчик бесплатных контактов увеличивается на 1.
- [ ] Три подтверждённые жалобы на одну компанию за 30 дней → её объявления пропали из поиска → после «Contact data is up to date» вернулись.
- [ ] Модератор блокирует компанию → объявления скрыты, в карточке красный флаг «Blocked».
- [ ] Детектор находит пару QuickRate по общему устройству и взаимным отзывам.
- [ ] Тесты: допуск к жалобе, возврат (деньги, квота, другой месяц), окно 30 дней, снятие скрытия, обнуление отзывов, признаки детектора.

2. **Страница `/subscriptions`:** список подписок с описанием фильтров, смена частоты, удаление.
3. **Сопоставление при размещении** (`postListing`): новое объявление проверяется по подпискам других компаний. При частоте «instantly» сразу создаётся уведомление `subscription_match` со ссылкой на объявление. При «hourly digest» объявление попадает в `pendingListingIds`, а процесс тика раз в час (при сдвиге ≥ 1 часа, см. DECISIONS) собирает уведомление `subscription_digest`.
4. **Почта:** для каждого уведомления о подписке вызывается `EmailChannel.send` (заглушка складывает письма в память). В лог пишется событие о «письме».

**Критерии готовности.**
- [ ] Перевозчик сохраняет подписку «Warsaw → любое, tent». Под грузовладельцем размещается подходящий груз. Под перевозчиком появляется уведомление со ссылкой.
- [ ] Неподходящее объявление уведомления не даёт, своё объявление — тоже.
- [ ] Дайджест: два подходящих объявления → одно уведомление после «+1 day».
- [ ] Тесты: сопоставление, частоты, исключение своих объявлений, формирование дайджеста.

## E10. Регистрация, деактивация, повторная проверка

**Цель.** Экран 1 из ТЗ и правила неактивных компаний.

**Что уже есть.** Адаптер `CompanyRegistry` и заглушка `MockRegistry` (известные номера из сида, исход для неизвестных по последней цифре — см. DECISIONS); `flagKindsFromVerification`, `profileMatchesRecord`; `loginAs` обновляет `lastLoginAt`; поиск скрывает объявления `deactivated` компаний.

**Сделать.**
1. **Регистрация** (`/register`, ссылка в «Log in as»): страна, тип и номер регистрационного номера, юридическое название, роль, контактное лицо и телефон. Вызывается `registry.lookup` (асинхронно), затем команда `registerCompany`. Результат проверки показывается сразу: найдено и совпадает / не совпадает / ликвидирована / не найдено; флаги ставятся по `flagKindsFromVerification`. Одна компания — один аккаунт: номер, уже зарегистрированный в стране, отклоняется. Новая компания становится текущей.
2. **Смена роли** в профиле своей компании.
3. **Деактивация:** процесс тика деактивирует компанию без входа 6 месяцев — статус `deactivated`, объявления скрыты, событие `company_deactivated`, уведомление.
4. **Восстановление:** при входе деактивированная компания видит баннер и кнопку «Verify again»: повторный `registry.lookup`, обновление `verification` и флагов, статус `active`, событие `company_reactivated`. Вход сам по себе не реактивирует.
5. **Ежедневная проверка по реестру:** процесс тика сверяет компании с реестром. Домен получает функцию синхронного поиска параметром; для заглушки это `MockRegistry.lookupSync`. Как это делать с реальным асинхронным реестром, описать в DECISIONS (фоновая задача вне тика).

**Критерии готовности.**
- [ ] Регистрация с номером, оканчивающимся на 9, даёт красный флаг «Not recommended»; на 0 — «Data not confirmed»; обычный номер — «Verified».
- [ ] Повторная регистрация номера Vistula Logistics отклоняется с понятным сообщением.
- [ ] Riga Container: «+1 week» → ещё активна; «+6 months» → деактивирована, объявления скрыты. Войти как Riga → «Verify again» → активна.
- [ ] Тесты: регистрация (все исходы реестра, дубликат), правило 6 месяцев (граница), реактивация.
